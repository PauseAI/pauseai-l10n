● Great question! Here's the history of DKIM and how it fits into the broader email authentication story:

  A Brief History of Email Authentication

  The Original Problem: SMTP Has No Security (1982)

  When SMTP (Simple Mail Transfer Protocol) was created in 1982, the internet was a small trusted network of academics. SMTP was designed with zero 
  authentication - any server could claim to send email from any address. This was fine when everyone knew each other!

  As the internet grew commercial in the 1990s, this became a massive problem:
  - Spammers could send millions of emails claiming to be from anyone
  - Phishers could impersonate banks perfectly
  - No way to verify "Is this email really from who it says?"

  The Three-Stage Solution

  1. SPF (Sender Policy Framework) - Early 2000s
  - Problem it solved: "Which mail servers are allowed to send for this domain?"
  - First mentioned: 2000 (mostly ignored)
  - Standardized: RFC 7208 in April 2014
  - How it works: DNS record lists authorized IP addresses
  - Limitation: Breaks when emails are forwarded (receiving server's IP doesn't match original sender's authorized IPs)

  2. DKIM (DomainKeys Identified Mail) - 2004-2007
  - Problem it solved: "Has this email been tampered with in transit?" + "Can forwarding work?"
  - Origins: Merger of two competing technologies:
    - Yahoo's DomainKeys (focused on combating phishing for banks/e-commerce)
    - Cisco's Identified Internet Mail (IIM) (focused on cryptographic signatures and reputation systems)
  - Merged: 2004
  - Standardized: RFC 4871 (May 2007), updated to RFC 6376 (September 2011, current standard: STD 76)
  - How it works:
    - Sending server signs email headers/body with private key
    - Receiving server verifies signature using public key published in DNS
    - Signature travels with the email, so forwarding doesn't break it!
  - Early adopters: Gmail, Yahoo, AOL, Fastmail (2007-2008)

  3. DMARC (Domain-based Message Authentication, Reporting, and Conformance) - 2010-2015
  - Problem it solved: "SPF and DKIM exist, but what should receivers DO when they fail?"
  - First discussed: 2010 (industry realized SPF/DKIM alone weren't enough)
  - Standardized: RFC 7489 (March 2015)
  - How it works: Policy published in DNS tells receivers: "If SPF/DKIM fails, quarantine or reject"
  - Bonus: Sends reports back to domain owners about authentication failures

  Why DKIM Was Specifically Created

  The forwarding problem:
  alice@bank.com → bob@gmail.com → bob@work.com
                       ↓
                  SPF checks IP of gmail.com (not bank.com) = FAIL ❌
                  DKIM checks signature from bank.com = PASS ✅

  The tampering problem:
  - SPF only checks IP addresses, not content
  - Malicious servers could modify subject/body after passing SPF
  - DKIM's cryptographic signature detects ANY modification to signed headers/body

  Modern Impact (2020s)

  By 2025, email authentication became mandatory for bulk senders:
  - Google/Yahoo require DKIM for >5,000 emails/day (since Feb 2024)
  - Non-authenticated email increasingly goes to spam
  - ~90% of domains now use at least one authentication method

  For PauseAI

  Without DKIM enabled:
  - ✅ Your emails still deliver (SPF likely working)
  - ⚠️ Lower trust score (no cryptographic proof)
  - ⚠️ Slightly higher spam risk
  - ❌ No protection if someone modifies email in transit

  With DKIM enabled:
  - ✅ Cryptographic proof emails came from pauseai.info
  - ✅ Better deliverability to Gmail/Outlook
  - ✅ Protection against content tampering
  - ✅ Foundation for adding DMARC later

  ---
  Fun fact: The merger of Yahoo and Cisco's technologies (creating DKIM) happened because both companies realized they were solving the same problem
  in slightly different ways. Rather than compete, they collaborated - a rare example of corporate cooperation on internet standards!

> Remind me of a Unix shell command to list which process ids are consuming the most memory (including their subprocesses) 

● Here are a few options for finding memory-consuming processes:

  Most common - ps with sorting:
  ps aux --sort=-%mem | head -20
  Shows top 20 processes by memory usage (RSS - Resident Set Size)

  top or htop (interactive):
  top
  # Then press 'M' to sort by memory
  # Or use htop if installed (more user-friendly)
  htop

  For process trees (including subprocesses):
  ps auxf --sort=-%mem | head -40
  The f flag shows the process hierarchy (tree view)

  Memory in human-readable format:
  ps aux --sort=-%mem | awk 'NR<=20{printf "%-8s %-8s %6s %s\n", $1, $2, $4"%", $11}'

● To kill all processes matching that command prefix:

  Using pkill with pattern matching:
  pkill -f "^/snap/firefox/6966/"

  Or with killall (simpler but less flexible):

  For more control, find PIDs first then kill:

  Notes:

  - Without -9, it sends SIGTERM (graceful shutdown)

  - The ^ in the pattern matches from the start of the command
