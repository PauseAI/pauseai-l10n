|---|---|
| Markdown posts | 96 files, ~82,500 words |
| UI strings (messages/en.json) | ~850 words |
| Content change rate (2025) | 157 active days, ~2.4 commits/day on those days |
| Typical daily delta | 2-3 posts touched, ~800 words each |

## What Scaling to "a Few Dozen" Locales Looks Like

**Daily incremental** (cache working, ~2,400 changed words × 30 locales × two-pass with overhead):
~230k word-equivalents/day

**Full retranslation** (new locale or model migration):
~83k words × two-pass × overhead ≈ ~300k word-equivalents per locale

Since switching model is trivial (one string in `llm-client.ts`, everything goes through OpenRouter), the main question is which model gives the best quality/speed/cost balance for translation specifically.

## Recommendation: **Google Gemini 2.5 Flash**

Available on OpenRouter as `google/gemini-2.5-flash-preview`.

**Why this model for translation:**

1. **Multilingual strength.** Google's models inherit from the deepest multilingual training corpus in the industry (Search, Translate, YouTube). For a project targeting dozens of locales including less-common ones, this matters more than benchmarks.

2. **Speed.** Flash models are designed for throughput. Your 1 req/sec rate limit would become the bottleneck, not the model — and you could potentially relax it.

3. **Instruction following.** The two-pass pipeline relies on the model preserving frontmatter keys, HTML tags, markdown links, and `{#slug}` anchors. Gemini 2.5 Flash is strong here.

4. **Cost.** Roughly $0.15/M input tokens, $0.60/M output tokens (via OpenRouter, may vary by provider). At 30 locales:
   - Daily incremental: **~$0.15/day** (~$4.50/month)
   - Full retranslation of one locale: **~$0.25**
   - Full retranslation of all 30 locales: **~$7.50**

   For comparison, Llama 3.1 405B was costing roughly 5-10x more for the same work.

5. **The two-pass pipeline is your quality safety net.** You don't need the most expensive model when you're already doing translate-then-review. A fast, competent model with two passes beats a slow, expensive model with one.

**Alternatives worth knowing about:**

| Model | Strength | Tradeoff |
|---|---|---|
| **Llama 3.3 70B** | Stays in your current ecosystem, very cheap (~$0.18/M) | Weaker on uncommon language pairs |
| **Claude Haiku 4.5** | Excellent instruction following, best at preserving markup | ~4x the cost of Gemini Flash |
| **DeepSeek V3** | Extremely cheap, strong on Asian languages | Variable quality for European languages, geopolitical considerations |

**What I'd avoid:** GPT-4o-mini (good but no particular advantage here), Claude Sonnet/Opus (overkill for cached incremental translation at 30 locales).

## 🤖 Claude

The OpenRouter tax is modest:

**Cost:** ~5.5% markup, applied at credit purchase time. Per-token rates are passed through at provider cost. So Gemini Flash at $0.15/$0.60 per M tokens direct would effectively be ~$0.16/$0.63 through OpenRouter.

**Latency:** ~25-50ms per request added. For your pipeline doing 1 req/sec on batch translation work, this is negligible — the model inference time dwarfs it.

**The real question is whether to keep OpenRouter at all.** Arguments each way:

**Keep OpenRouter:**
- Single API key, single billing — no per-provider account management
- Easy to swap models by changing one string (you've already built around this)
- 5.5% on your projected ~$4.50/month at 30 locales is ~$0.25/month — truly nothing

**Go direct:**
- Google's Gemini API has a generous free tier (may cover your daily incremental entirely)
- Direct access to latest model versions sooner
- One fewer dependency in the chain

Given your volume, the 5.5% is pocket change either way. I'd say **keep OpenRouter for now** — the flexibility to try different models without code changes is worth more than $3/year in savings. If you later scale dramatically or want to exploit Google's free tier, switching to direct is straightforward.

## 🤖 Claude

Good news on all three fronts:

### 1. URL Route Translation

Your current prompt already shouts about it ("I repeat: DO NOT CHANGE LINK TARGETS"), and the `utils.ts` pre-processor injects inline hints like `<!-- don't localize target, only label -->`. The fact that Llama 405B *still* mangled URLs says more about that model's instruction following than the prompt. Gemini 2.5 Flash and modern Claude models are significantly better at respecting structural constraints — this is one of the areas where 12 months of progress genuinely shows. You'd likely be able to *simplify* the prompt rather than add more guardrails.

### 2. Prompt Caching via OpenRouter

**OpenRouter supports it and won't get in the way.** Specifically:

- **Gemini 2.5 Flash has implicit caching** — it happens automatically with no code changes. Minimum 1028 tokens (your translation prompts easily exceed this). OpenRouter uses "sticky routing" to keep subsequent requests on the same endpoint so the cache hits.
- **Claude models support explicit caching** via `cache_control` breakpoints with a 1-hour TTL.

So the "ten great example translations as a style reference" pattern would work well — put the examples in a system message prefix, and they'd be cached across all subsequent file translations in a run. Your pipeline already processes files sequentially at 1 req/sec, so the cache would stay warm throughout a batch. This would need a modest code change to structure the prompt into a cacheable prefix + per-file content, but the architecture supports it.

### 3. Bespoke Translation / ELI5 / Audience Adaptation

This is really "conditional rewriting during translation" rather than pure l10n, and it's where a more capable model matters. Gemini 2.5 Flash could handle it today — it's strong at following nuanced instructions like "translate this to German at a reading level suitable for a general audience without technical background." The two-pass pipeline actually helps here: pass 1 translates with the audience adaptation, pass 2 reviews for both accuracy and appropriate register.

The architecture would extend naturally: your `promptAdditions` system (currently empty maps in `additions.ts`) was designed exactly for per-page or per-language extras. An ELI5 variant could be a parallel output alongside the standard translation — same source, different prompt addition, different output path in the cage (e.g., `l10n-cage/md/de-eli5/`).

The bigger question there is UX and routing, not the LLM capability.

**Bottom line:** Gemini 2.5 Flash via OpenRouter gives you better instruction following (fixing the URL problem), native prompt caching support (enabling style-reference patterns), and enough capability for audience-adaptive translation — all at lower cost than the current setup.
